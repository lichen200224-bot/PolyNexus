# D2B-01 Runtime Dispatch Authorization repair

Architecture decision: `D2B01-ARCH-01-RUNTIME-DISPATCH-AUTHORIZATION` (`AUTHORIZED_FOR_BOUNDED_IMPLEMENTATION`). This receipt describes a Core product dispatch gate. ChatGPT development authorization permits implementing this repair; it is not approval for a particular product Run. Candidate Human Accept is a separate action and is not used here.

The original product path persisted `runtime.routing_policy` with `APPROVAL_REQUIRED` and stopped at `NEED_ACTION`. This correctly avoided external effects, but there was no durable way to authorize one exact Run under one exact policy decision. The adapter-only real gate therefore did not prove production dispatch.

`RuntimeDispatchAuthorization` is a separate durable record, bound to Run, Task, generation revision, RuntimeProfile identity and revision, exact routing-policy Evidence, a canonical digest of the effective policy facts, issuer, issue/expiry times, and state. It is single-use and has a bounded TTL. Its scope cannot be edited or transferred; state transitions and issue/consume/revoke events remain auditable. It carries no runtime credential, Candidate Accept, verification, assurance, or global policy override.

The original policy disposition remains authoritative: `ALLOW` dispatches without this authorization; `DENY` never dispatches; `APPROVAL_REQUIRED` without a fresh exact authorization yields `NEED_ACTION`, leaves the Run `CREATED`, and creates no claim, binding, or external process. With a fresh exact authorization, the effective dispatch gate permits this Run while preserving `APPROVAL_REQUIRED` in `runtime.routing_policy`. If policy facts drift on retry, authorization becomes stale; if policy becomes `DENY`, denial takes precedence.

The dispatch transaction validates an `ISSUED` authorization, claims the generation, transitions the Run `CREATED`→`STARTING`, inserts the immutable RuntimeBindingSnapshot, consumes the authorization, and writes `runtime.dispatch_authorization` Evidence and an audit event. External adapter construction and launch occur only after commit. A rollback leaves the authorization issued, the Run unclaimed, and no binding or external effect. Repeating a committed start cannot consume the grant or insert another binding.

Production issuance uses the existing D1B A-LP authenticated Human principal proof for the distinct `runtime-dispatch` audience; it does not call Candidate Accept. `TEST_ONLY` issuance is explicitly labelled and restricted to an isolated technical SQLite database under the test-only environment gate. It is valid for automated tests and diagnostic integration, never Human UAT or production Human approval. A real Human-facing Run Preparation and Work Control UX is deferred to D4. This repair adds no Web UI or product-version change.
