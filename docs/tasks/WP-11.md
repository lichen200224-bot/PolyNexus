## Three legal top-level modes

**Only these are legal at the top-level `Task.mode` contract:**

1. `DISCUSS` — Independent analysis → Cross Review → Consensus / Disagreement / Risks / Missing Info → Human Decision (scope baseline §3.1)
2. `REVIEW` — Artifact / Code / Document → Findings / Severity / Blockers / Recommendations (§3.2)
3. `VALIDATE` — Tool / Command / Rule / Document Check → Evidence → `PASS / FAIL / NEED_ACTION / HUMAN_DECISION` (§3.3)

Notes:
- Case-sensitive, upper-case only. Lower-case (`discuss`), mixed (`Review`), or whitespace-padded (` REVIEW `) are **not** legal and must be rejected via `422` (string enum exact match).
- `Develop`, `ANALYZE`, `PLAN`, `EXECUTE`, or any other string is **not** a legal top-level mode. `Develop` is explicitly a Workflow action / Agent role per scope baseline, not a fourth mode. Implementation and tests must prove its rejection.

## Illegal mode — 422 contract

Any `mode` value that is not one of `["DISCUSS","REVIEW","VALIDATE"]` when provided must fail **before** persistence:

- **HTTP**: `422 Unprocessable Entity`
- **Body detail** (from `services/core/src/polynexus_core/api/tasks.py:77-80`): `Invalid mode: {body.mode}. Must be one of: DISCUSS, REVIEW, VALIDATE`
- **No partial write**: the Task row is not created, no event is persisted, no secret or internal error is leaked.
- Applies to: `INVALID`, `DEVELOP`, `discuss`, `review`, `validate`, `DISCUSS `, ` REVIEW` — `null` is **not** illegal — see omitted-mode rule; JSON non-string types are rejected by Pydantic validation (also `422`).
- Note: `""` (empty string sent as explicit JSON string) is **not** `422` under current code — `services/core/src/polynexus_core/api/tasks.py:72` checks `if body.mode:` (falsy), so `""` is treated as omitted → `201` with `mode == "REVIEW"`. This is recorded as the contract under “Omitted mode” below. If `""` must be `422`, stop and report `NEED_ACTION` for a Human/Codex decision before modifying `api/tasks.py`; do not change product source in this doc-only step.

Existing test reference: `services/core/tests/test_api.py:335` `test_create_task_invalid_mode` already proves `mode=INVALID` → `422`.

## Persistence / reload and API contract

### Persistence contract

- `Task.mode` is stored as `String(32)` `mode` column (`persistence/models.py`), value is `WorkMode.value` (`"DISCUSS"|"REVIEW"|"VALIDATE"`).
- Conversion is explicit: write `t.mode.value`, read `WorkMode(r.mode)`.
- No migration, no new column, no ORM dependency in Domain.
- Ordering and listing are unchanged; reload via `SqlTaskRepository.list_by_project(project_id)` and `SqlTaskRepository.get(task_id)` must return the same `mode` that was persisted.

### Reload proof

- Create Project, then create Task with each of the three modes (and one with omitted mode).
- Commit, **close and reopen** the SQLAlchemy session / database file.
- `GET /projects/{project_id}/tasks` and `GET /tasks/{task_id}` both return the persisted `mode` verbatim.
- No fabricated or inferred mode; no coupling to workflow_id or other fields.

### API contract

- `POST /api/v1/projects/{project_id}/tasks`:
  - Auth: existing `AuthLoopback` — `403` without token (fail closed).
  - Parent project missing: `404`.
  - Valid `mode` (including omitted): `201` with `TaskResponse.mode` = the persisted string.
  - Invalid `mode`: `422` with `Invalid mode` detail, no row created.
- `GET /api/v1/projects/{project_id}/tasks` and `GET /api/v1/tasks/{task_id}`:
  - Return `mode` as a string (`DISCUSS|REVIEW|VALIDATE`) exactly as stored; `403/404` preserved.
