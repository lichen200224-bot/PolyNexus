## Goal

Implement the first deterministic workflow-gate contract. A workflow must be able to evaluate required evidence, block a verified verdict when a hard gate fails or is missing, require an explicit Human gate decision where configured, and preserve a truthful durable result. AI opinion or synthesis must never convert a failed deterministic gate into PASS.

WP-13 is a Core contract/policy task. It does not implement runtime adapter conformance, provider integrations, Browser E2E, frontend changes, or the Doctor/conformance matrix owned by later work packages.

Current implementation facts that the task must respect:

- `WorkflowDefinition` currently retains step `id`, `type`, and `depends_on`; `EVIDENCE_CHECK` and `HUMAN_GATE` step semantics are not yet executed by `ReferenceWorkflowExecutor`.
- `schemas/workflow.schema.json` allows the fixed V1 node types and step extensions, including `EVIDENCE_CHECK` and `HUMAN_GATE`.
- Existing reusable evidence boundaries are `EvidenceType` (`AI_OPINION`, `RUNTIME_EVIDENCE`, `TOOL_EVIDENCE`, `DOCUMENT_EVIDENCE`, `HUMAN_EVIDENCE`) and `EvidenceStatus` (`PASS`, `FAIL`, `NEED_ACTION`, `HUMAN_DECISION`, etc.).
- The current Domain model has no independent persisted `Decision` or `Verdict` entity, and `RunResult` has no dedicated verdict-authority field. Do not overload `RunResult.summary` with a secret, fabricated verdict, or implicit Human approval.

The following is a proposed baseline contract, not permission to change a frozen public contract:

1. `EVIDENCE_CHECK` reads actual persisted evidence scoped to the current Task/Run. It does not infer evidence from `AI_OPINION`, prose, participant consensus, or synthesis text.
2. A configured hard gate is satisfied only by the required deterministic evidence, normally `TOOL_EVIDENCE` with an explicit `PASS` and valid command/exit metadata where the workflow requires it.
3. Explicit hard-gate `FAIL` must produce a non-PASS outcome. Missing, malformed, stale, cross-run, or unverified evidence must also produce a non-PASS outcome.
4. `HUMAN_GATE` cannot auto-pass under D11 Option C. The current `Evidence.actor_id` boundary cannot verify a Human principal, so every HUMAN_EVIDENCE approve/reject remains `HUMAN_DECISION` / `NEED_ACTION`; no actor string, prefix, allow-list, deny-list, or metadata field may produce PASS/VERIFIED or deterministic FAIL. A future verified rejection requires a separate Option A/B architecture decision.
5. A `VERIFIED`/PASS verdict is legal only after every required deterministic hard gate passes and every configured Human gate is explicitly approved. Synthesis and Council output may explain evidence but cannot override a failed or missing gate.
6. The exact mapping among `FAIL`, `NEED_ACTION`, and `HUMAN_DECISION` for missing evidence, explicit failure, and pending/rejected Human gates must be made explicit in tests and in the handoff. If that mapping changes D06, ADR-009, or a stable API/persistence contract, stop with `NEED_ACTION` and request the required Human decision before source changes.

Preferred implementation direction: extend the existing Workflow/Run/Evidence/Event boundaries. Do not introduce vendor-specific Core branches, arbitrary script nodes, a second evidence ledger, or a new persistence subsystem.

## Acceptance matrix

The implementation must add deterministic tests for at least the following. Test names may differ, but each behavior must be directly asserted.

1. Valid fixed workflow nodes load and preserve the required `EVIDENCE_CHECK` hard-gate and `HUMAN_GATE` configuration.
2. Invalid gate configuration, duplicate gate identifiers, missing dependencies, and unsupported node types fail closed before execution.
3. A required `TOOL_EVIDENCE` with valid PASS metadata satisfies the matching hard gate.
4. A required tool evidence with explicit FAIL blocks PASS and cannot be overridden by AI opinion, Council consensus, or synthesis text.
5. Missing, malformed, stale, cross-task, cross-project, or cross-run evidence produces the documented non-PASS outcome.
6. `AI_OPINION` never satisfies a deterministic hard gate, even when its text says PASS.
7. A configured Human gate is pending without explicit Human evidence/decision and cannot auto-pass.
8. Unverified Human approve/reject blocks progression; both remain non-PASS under D11 Option C. A future verified approval/rejection requires a separate approved identity boundary decision.
9. A VERIFIED/PASS result is impossible when any required gate is failed, missing, unverified, or backed only by AI opinion.
10. Synthesis/Council output cannot mutate a failed or pending gate into a verified result.
11. Gate outcome, verdict authority, and required evidence references survive session close/reopen through the accepted durable boundary.
12. Replaying the same gate evaluation is idempotent within the PARTIAL_INTEGRITY threat model (Human Option B) and does not duplicate terminal RunEvents or fabricated evidence. Full-consistent 8-field rewrite including both provenance hashes is an accepted limitation outside this guarantee.
13. Partial/failed/timed-out/cancelled required Runs remain truthful and cannot produce a verified verdict.
14. Secret-marker injection proves raw exception text, token fragments, and credential values are absent from results, events, evidence, artifacts, API responses, and persisted rows.
15. Existing WP-08A/B, WP-09B/C/D, WP-11, and WP-12 tests remain green.

## Threat Model Boundary (Human Option B — 2026-08-24)

Maturity label: **PARTIAL_INTEGRITY**.

### In scope (verified)

- Single-field tamper (actor_id, source, task_id, run_id, bound_task_id, bound_run_id, identity_hash, provenance_token) → fail-closed ✓
- Partial multi-field tamper (misses ≥1 provenance hash field) → fail-closed ✓
- Cross-task/run isolation (corrupted Task A does not block Task B) ✓
- Same-task multi-run isolation (corrupted run1 does not block run2) ✓
- Ordinary DOCUMENT_EVIDENCE with overlapping metadata does not block persist ✓

### Out of scope (NOT detectable)

- Actor with SQLite direct write access who consistently rewrites ALL 8 fields
  (actor_id, source, row task_id/run_id, bound_task_id/bound_run_id,
  identity_hash, provenance_token) simultaneously. Such an actor can produce
  a fully consistent record that evades all current detection signals.
  A new report WILL be created alongside the orphaned tampered one.
  This behavior is documented in test_full_consistent_tamper_creates_new_report_documented_limitation.
