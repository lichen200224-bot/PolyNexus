## Council contract to implement

### 1. Participant bounds and identity

- A Council run contains 2–4 participants/roles.
- Every participant has a stable run-scoped identity and an explicit role label.
- Participant outputs remain attributable to the originating participant and Council round.
- Duplicate participant identity in one round is rejected deterministically before execution or persistence.

### 2. Deterministic stage ordering

The normal stage order is:

~~~text
independent analysis
  → cross review
  → synthesis
~~~

- Independent analysis must not consume another participant's in-progress output.
- Cross Review may reference completed analysis outputs only.
- Synthesis may reference analysis and cross-review outputs only after the required stage completes.
- Stage order and participant/round correlation must be represented in durable Run events or the existing equivalent history boundary.

### 3. Partial outcomes

Each participant outcome must distinguish at least:

- completed with an actual output reference;
- failed with a normalized, non-secret reason;
- timed out or cancelled with an explicit terminal reason;
- unavailable/not executed when the orchestration policy prevents execution.

The exact public enum or response field names must follow existing Core contracts. If implementing this requires a new Domain entity, migration, public REST schema, or new lifecycle state, stop and return NEED_ACTION for an architecture decision before changing source.

### 4. Synthesis truthfulness

- A partial Council result identifies missing/failed participants and does not silently present the result as unanimous.
- If synthesis cannot run because required inputs are missing, persist a truthful failed/partial outcome; do not fabricate a summary, Finding, Evidence, Artifact, or consensus.
- AI_OPINION remains distinct from TOOL_EVIDENCE, RUNTIME_EVIDENCE, DOCUMENT_EVIDENCE, and HUMAN_EVIDENCE.
- WP-12 does not grant VERIFIED status or hard-gate authority to an AI synthesis.

### 5. Bounded execution

- Council rounds, participant count, and timeout behavior must be bounded by explicit configuration or the existing workflow definition.
- No unbounded loop, implicit retry storm, or hidden provider fallback may be introduced.
- Repeating the same command preserves stable Task/Run identity and does not duplicate participant execution when the existing idempotency contract applies.

### 6. Persistence and reload

- Participant outcomes, stage events, references, and partial/failure state survive session close/reopen when the chosen contract makes them durable.
- Reload preserves deterministic ordering and Task/Run ownership.
- No participant output may be persisted under another participant, task, project, or run.

## Implementation evidence (Attempt 7 — Codex FAIL repair)

Codex review of Attempt 6 returned `FAIL` with two MAJOR issues. Both fixed in Attempt 7.

### MAJOR Issue 1 — non-COMPLETED Run mislabeled COMPLETED

`_run_analysis_stage()` previously unconditionally set `participant.outcome = COMPLETED`, `participant.output_ref = run.id`, and `evidence_to_persist = execution.evidence` after `RunSupervisor.execute_run()` returned, even when `execution.run.state` was `FAILED`/`TIMED_OUT`/`CANCELLED`.

Fix (`services/core/src/polynexus_core/council/orchestrator.py`): the `else` branch now branches on `execution.run.state`:
- `COMPLETED` → `ParticipantOutcome.COMPLETED`, set `output_ref`, persist execution evidence only.
- `FAILED` → `ParticipantOutcome.FAILED` + sanitized fixed reason; no `output_ref`.
- `TIMED_OUT` → `ParticipantOutcome.TIMED_OUT` + sanitized fixed reason; no `output_ref`.
- `CANCELLED` → `ParticipantOutcome.CANCELLED` + sanitized fixed reason; no `output_ref`.
- Unexpected intermediate state → contained as FAILED.
Non-COMPLETED participants never set `output_ref`, never enter Cross Review (cross-review selects only `outcome is COMPLETED`), and never produce fabricated consensus (synthesis stays truthful partial / truthful failed).

### MAJOR Issue 2 — sanitized failure breaking Run event lifecycle

`_apply_sanitized_failure()` previously did `run.state = RunState.FAILED` directly and only replaced an already-existing FAILED event. When the adapter-boundary exception occurred while the Run was still CREATED/STARTING/RUNNING (no FAILED event), the persisted Run state became FAILED while the last event stayed RUNNING, violating ADR-007 durable event history.

Fix (`services/core/src/polynexus_core/council/orchestrator.py`):
- Added `_sanitize_terminal_reason(run, reason)` to replace the reason on an already-legal terminal event (FAILED/TIMED_OUT/CANCELLED) while preserving the original event id / occurred_at / ordering and terminal state. Used for terminal states returned by `execute_run()` whose reason may come from raw `status.error`.
- Rewrote `_apply_sanitized_failure(run, reason)`:
  - If `run.state in {COMPLETED, TIMED_OUT, CANCELLED}` → returns WITHOUT regressing a terminal Run to FAILED.
  - If a raw FAILED event already exists → sanitizes it in place (id/occurred_at/order preserved).
  - Otherwise applies the legal lifecycle CREATED→STARTING→RUNNING→FAILED (or available prefix) so exactly one FAILED terminal event is appended and `state`/`updated_at` stay consistent with the last event.

### Supervisor hardening (WP-09B scope impact disclosed)

## Implementation evidence (Attempt 8 — Codex FAIL repair)

Codex review of Attempt 7 returned `FAIL` with two further MAJOR issues. Both fixed in Attempt 8.

### MAJOR Issue 1 — raw status.error leaked into persisted run.result

`RunSupervisor.execute_run()` returned `RuntimeResult(summary=status.error or status.state)` for FAILED/TIMED_OUT terminal statuses. `SqlRunRepository` persists `run.result.summary` into `RunRow.result_summary`, so a raw secret in `status.error` leaked. The orchestrator previously only sanitized the terminal event reason and left `run.result` populated.

Fix (`services/core/src/polynexus_core/council/orchestrator.py`): in the analysis `else` branch, every non-`COMPLETED` outcome (`FAILED`/`TIMED_OUT`/`CANCELLED` and the fallback) now sets `run.result = None` before persistence. The sanitized terminal event reason is preserved; `evidence_to_persist` stays empty so no `RUNTIME_EVIDENCE` is written; with `run.result = None` there are no dangling `finding_ids`/`evidence_ids`/`artifact_ids`.

### MAJOR Issue 2 — generic exception handler rewrote an already-terminal TIMED_OUT/CANCELLED participant to FAILED

The generic `except Exception` handler unconditionally called `_apply_sanitized_failure` (running its no-regress guard) and set `ParticipantOutcome.FAILED`. When `status()` returned `TIMED_OUT`/`CANCELLED` and a later `version_info()` raised inside `RunSupervisor._build_execution_from_existing`, `run.state` was already `TIMED_OUT`/`CANCELLED` but the participant outcome became `FAILED` — inconsistent.

Fix (`services/core/src/polynexus_core/council/orchestrator.py`): the generic handler now maps the participant outcome to the Run's ACTUAL terminal state:
- `run.state == FAILED` → `ParticipantOutcome.FAILED` + sanitized FAILED reason
- `run.state == TIMED_OUT` → `ParticipantOutcome.TIMED_OUT` + sanitized timeout reason
